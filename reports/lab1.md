# Lab1 实验报告

# 实验目的

本实验为每个任务增加独立的系统调用计数，实现sys\_trace系统调用，读取用户程序指定地址的一个字节，向用户程序指定地址写入一个字节，以及查询当前任务对指定系统调用的累计调用次数。

# 简答题

1\.使用的是RustSBI 0\.4\.1。ch2b\_bad\_address会向0x0地址写数据，运行后出现PageFault，输出中的错误地址也是0x0，然后这个应用被内核终止。ch2b\_bad\_instructions 尝试在U态执行sret，ch2b\_bad\_register 尝试读取sstatus，这两个程序都会出现IllegalInstruction，并被内核终止。

2\.1刚进入 \_\_restore 时，sp 指向内核栈上保存的TrapContext。一种情况是，Trap已经处理完成，trap\_handler返回后会接着执行\_\_restore；另一种情况是，应用第一次运行，\_\_switch会恢复提前准备好的任务上下文，其中ra指向 \_\_restore，sp指向初始的TrapContext。

2\.2 处理了sstatus、sepc 和 sscratch；因为sstatus\.spp决定sret后程序返回哪个特权级；因为sepc 表示回到用户态后从哪条指令继续执行；因为sscratch 存放之前保存的用户栈指针，最后会和当前的内核栈指针交换。

2\.3 x2就是sp，恢复其他寄存器时还需要通过它访问内核栈上的TrapContext；x4是tp，未使用到，不需要使用。

2\.4 sp中变成用户栈指针，sscratch中则保存内核栈顶。这样返回用户态后程序可以继续使用自己的栈，下次发生Trap时又可以通过交换快速找回内核栈。

2\.5 sret

2\.6 sp 变成内核栈指针，后面可以在内核栈上保存rapContext；sscratch则暂时保存用户栈指针，之后再把它写入TrapContext的x2位置。

2\.7 发送系统调用，异常或者终端时，会执行ecall触发trap，从 U 态进入S态

# 实验思路

首先运行 make \-C ci\-user test CHAPTER=3 进行测试，从输出中找到最早出现的 panic 和对应行号，查看失败断言及其期望结果，再使用vscode全局搜索搜索相关函数，沿着用户态的 count\_syscall、trace、sys\_trace、ecall 以及内核的系统调用入口一步步分析。根据测试的要求，在控制块中增加系统调用计数数组，使每个任务独立保存各种系统调用的次数；在任务管理器中实现当前任务计数的增加和查询，并在系统调用入口完成计数，随后实现 sys\_trace 的系统调用次数查询、用户内存读取和用户内存写入三种功能。完成修改后，使用 cargo fmt \-\-manifest\-path os/Cargo\.toml 格式化代码，然后重新执行官方测试，根据输出继续定位和修改问题，直到所有测试通过。



# 实验感悟

实验的代码量不大，但涉及到了用户态与内核态之间的数据传递，明白了系统调用时通过寄存器传参、ecall 和 trap 完成用户态到内核态的切换；学习到了先进行测试失败，通过观察panic代码，以及测试代码，分析作者意图；在实现过程中，测试失败时应先寻找最早出现的 panic，定位错误位置进行解决；理解UN撒份额1并不自动保证操作正确，只是表示程序员要承担编译器无法验证的责任。
