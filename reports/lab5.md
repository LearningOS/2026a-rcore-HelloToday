# lab5

# 功能总结

实验在进程 PCB 中为 mutex 和 semaphore 分别维护 Available、Allocation、Need。创建线程时补矩阵行，创建同步对象时补资源列；lock/down 到来时先登记 Need，运行安全性算法，若不存在让所有线程完成的安全序列就返回 \-0xDEAD。真实申请成功后再同步更新资源账本。semaphore 阻塞场景需要在 up 弹出等待者时先完成许可交接，再唤醒线程，避免重复或滞后记账。

# 问答题

## 问题1 主线程退出后，资源回收相关问题

1\.回收的资源包括回收进程内其他线程的用户栈、TrapContext、tid 等线程用户资源，移除就绪队列和定时器队列中的线程引用，回收进程地址空间中的代码、数据和用户页，关闭文件描述符，并释放进程持有的 mutex、semaphore、condition variable 等对象以及 PCB 内的线程表

2\.其他线程的 TaskControlBlock 可能被进程控制块的 tasks 数组、调度器的就绪队列、定时器队列，以及互斥锁、信号量和条件变量的等待队列引用。

3\.主线程退出时，需要清空 tasks 数组，并主动删除就绪队列和定时器队列中的引用，防止已退出进程的线程再次被调度或唤醒。同步对象的等待队列不需要逐个清理，因为这些同步对象只属于当前进程；当进程控制块最终被回收时，同步对象会一同销毁，其等待队列中的 Arc\<TaskControlBlock\> 也会自动释放。



## 两种Mutex的实现的区别

1\.Mutex1 在解锁时先将 locked 设置为 false，再唤醒等待线程。被唤醒的线程需要重新检查锁状态并参与竞争，因此新到达的线程可能先取得锁，导致原等待线程再次阻塞，甚至出现饥饿。

2\.Mutex2 在存在等待线程时不会将 locked 设置为 false，而是保持锁定状态并直接唤醒队首线程，相当于将锁直接交给该线程。这样可以避免其他线程插队，但要求被唤醒线程一定能够继续运行并接管锁；如果发生异常唤醒或线程无法继续执行，锁可能一直保持锁定，导致其他线程永久阻塞。
